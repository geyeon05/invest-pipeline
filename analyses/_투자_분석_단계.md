# 투자 분석 단계

사용자 결정 2026-11-20. 단계마다 사용자가 하나씩 정했다. 바꿀 때는 사용자와 정한 뒤 이 문서를 고친다.

## 시작

- **"투자 분석 시작 회사이름"**: 1단계부터 한다. 단, `analyses/_보유목록.md`에 있는 회사면 **6단계(보유 중 점검)**로 바꾼다.
- **"보유 점검 회사이름"**: 6단계부터 한다.
- 회사 폴더: `analyses/회사이름/`
  - `진행.md`: 지금 몇 단계인지, 정한 것, 역할 기록
  - `분석기록.md`: 날짜별 초안·피드백·확정 판단, 다시 볼 조건
  - 결과물(5단계): 분석 보고서·검증표·역할구분 (md + PDF)
- 새 창에서 다시 시작하면 **`진행.md`를 먼저 읽고** 이어서 한다.
- `analyses/` 안의 기록은 개인 투자 정보라 **GitHub에 올리지 않는다** (`.gitignore`). 이 설명서만 올린다.

## 모든 단계 공통

- 바꾸는 작업(파일 생성·수정, 자료 받기, 커밋·푸시)은 **승인 후**에 한다. 자료를 받을 때는 요청 수를 먼저 알린다.
- 설명은 쉬운 말로 하고, 사용자가 **이해했다고 말한 뒤** 다음으로 넘어간다.
- 판단은 **초안 → 피드백 → 확인할 것 → 확정**을 거친다.
  - 피드백은 정답이 아니라 반대되는 사실, 빠진 자료, 내 성향(`investor_profile.md`)과 어긋나는 점을 짚는다.
  - '확인할 것'은 기존 부품 / 자료 받기(승인) / 새 도구(옮겨 적기·임시·정식 중 의논)로 처리한다.
  - **확인할 것이 하나라도 남으면 확정하지 않는다.**
- `진행.md`에 단계마다 **'사용자가 정한 것·판단한 것'**과 **'AI가 한 것'**을 나눠 기록한다.
- 모든 수치에는 출처를 단다 (`CLAUDE.md` 2장).

## 공책 양식 (사용자 결정 2026-11-20)

회사마다 공책 한 권. 엔진(계산)·화면·Claude Code가 **같은 공책을 읽고 쓴다.** 그래서 칸을 미리 정해 둔다.

| 쪽 | 칸 |
|---|---|
| 표지 | 회사, 지금 어디까지(회차·단계), 지난 최종 판단, 다시 볼 조건, 보유 여부 |
| 회차 | 다시 분석하면 **새 회차**를 만든다. 지난 회차는 그대로 남겨 비교한다. 회차마다 '처음부터 / 바뀐 부분만' |
| 단계 쪽 (1~8) | 계산 결과(숫자는 사실로), 출처, **논의 항목 = 켜진 신호 하나하나**(사용자 결정 2026-11-20). 신호가 없으면 단순 정보(**'확인함 + 날짜'**). 항목마다 판단 기록(초안 → 피드백 → 고친 판단 → 확정, 날짜와 함께 쌓임)과 확인할 것(처리 방법·상태·결과와 출처). 엔진이 남긴 단계 전체의 확인할 것(덜 받은 자료 등)이 남으면 그 단계는 확정·확인함 불가 |
| 최종 판단 쪽 | 모아 본 것, 판단 기록, 결론, 다시 볼 조건, 결과물 위치 |
| 보유 점검 쪽 | 점검 날짜, 점검 이유, 산 이유가 여전한지, 판단 기록, 결론 |
| 역할 기록 쪽 | 날짜, 단계, 누가(사용자 / AI), 한 일. 공책에 적을 때 **자동으로** 남는다 |

- 파일: `analyses/<회사이름>_<회사ID>/notebook.json` (형식 세부는 `criteria/README.md` 4장 'AI가 정한 값')
- 공책은 **`data.py run`(엔진)과 `data.py note`(판단 적기)로만** 고친다. 손으로 고치지 않는다.
  - 확인할 것이 남으면 `note --confirm`이 거절된다. 피드백 전에는 확정할 수 없다.
- **"○○ N번 M항목 피드백해줘"를 받으면 (Claude):** `note 회사 --step N`으로 초안을 읽는다 (항목은 `--item M`) → 필요하면 부품으로 사실을 확인한다 → 대화창에 피드백을 보여주고 `note --feedback`(긴 글은 `--text-file`)으로 적는다 → 확인할 것은 `note --add-check … --method …`로 적고, 확인하면 `--done-check`로 결과와 출처를 적는다. 화면은 몇 초마다 공책을 다시 읽어 저절로 보여준다.
- 화면: `uv run server.py` → http://localhost:8501 (내 컴퓨터에서만).
- 보유 점검(6단계): 최종 판단이 '산다'면 화면에 '샀다'(날짜) 버튼 → 보유 중이면 '보유 점검 시작'(정기/바로). 대화창에서는 `uv run data.py hold 회사 --bought YYYY-MM-DD` / `hold 회사 --check 정기|바로` / `hold list`. 점검 항목 피드백은 `note 회사 --step h1 --item M --feedback "…"`, 결론 확정은 `--confirm "…" --conclusion 계속 보유|일부 판다|판다`.
- 결과물 3종(5단계 7)은 최종 판단을 확정하면 화면의 **'결과물 만들기'** 버튼으로 만든다 (사용자 결정 2026-11-20). 분석 보고서 순서: 결론 → 단계별 확정 판단(사실 + 내 판단) → 가격 판단 → 금리·환율 → 다시 볼 조건. 검증표는 엔진이 쓴 공시 값을 원본과 다시 대조하고, 판단 글에 직접 쓴 숫자는 '확인 필요'로 모은다 → 그 숫자는 Claude가 원문과 대조한다. 시안(기업분석 진행 화면)을 옮긴 HTML(`web/`). 화면에서는 초안·고친 판단·확정·확인함·다시 열기만 적고, 피드백은 적을 수 없다.
- 과제 공책도 같은 양식을 쓴다 (`cases/_과제_진행_단계.md`).

## 9단계 (2026-11-20 확정, 바뀔 수 있음)

1 약속 이행 · 2 현금 창출 · 3 자본 배분 · 4 이익의 질 · 5 재무 안전성 · 6 특수관계자 · 7 정성 자료 · 8 가격 판단 · 9 최종 판단

엔진이 아직 없으면 있는 부품(`criteria/README.md` 2장)으로 단계마다 손으로 계산한다.

## 1단계: 분석 시작하기

1. 회사를 검색한다. 후보가 여러 개면 목록을 보여주고 **사용자가 고른다**.
2. 이 회사를 전에 분석한 기록(`분석기록.md`)이 있으면 보여준다: 언제 분석했는지, 최종 판단, **다시 볼 조건**.
   - 다시 볼 조건이 있으면 그 조건부터 확인한다.
   - **처음부터 다시 분석할지, 바뀐 부분만 할지 사용자가 그때마다 고른다.**
3. 받아야 할 자료와 요청 수를 알리고 승인받은 뒤 받는다.

끝: 자료를 다 받으면.

## 2단계: 9단계 계산과 단순 정보 확인

1. 1~8단계를 계산한다.
2. 단계마다 **단순 정보**(기준 충족)와 **논의할 부분**(경고, 판단 필요)으로 나눈다.
3. 1번 약속 이행에서 **탈락하면 알리고, 계속할지 사용자에게 묻는다.**
4. 단순 정보를 쉬운 말로 보여준다 → 사용자가 확인한다.

끝: 사용자가 단순 정보를 확인하면.

## 3단계: 논의할 부분

1. 논의할 단계가 여러 개면 **어떤 순서로 할지 사용자가 그때마다 고른다.**
2. 단계마다 초안 → 피드백 → 확인할 것 → 확정.
3. 경쟁사 비교는 피드백에서 필요하다고 나오면 '확인할 것'으로 받는다. **경쟁사는 사용자가 고른다.**

끝: 논의할 부분(8번 제외)을 모두 확정하면.

## 4단계: 가격 판단 (9단계 8번)

1. 주가 자료의 요청 수를 알리고 승인받은 뒤 받는다.
2. PER·PBR의 **5년 추이**를 보여준다 (`price`). 경쟁사 비교는 **필요하면 그때** 한다 (`price --peers`, 경쟁사는 사용자가 고름).
3. 숨은 자산이 있으면 조정 PBR을 계산한다. **반영할 금액은 사용자가 정한다.**
4. 7번 정성 자료의 장부 밖 가치를 가격의 단서로 함께 보여준다.
5. "지금 비싼가?" 초안 → 피드백 → 확인할 것 → 확정.
6. 적정 가격 기준(내재가치·안전마진)은 보류 중이다. 13~14주차 뒤에 정해서 이 단계에 추가한다. 그전까지는 잠정 판단이다.

끝: 가격 판단을 확정하면.

## 5단계: 최종 판단 (9단계 9번)

1. 3단계와 4단계를 **모두 확정해야** 시작한다.
2. 한 장에 모아 보여준다: 단순 정보 요약, 확정한 판단, 가격 판단, **금리·환율(사는 시점 참고용)**.
3. 사용자가 결론 초안을 쓴다: **산다 / 기다린다 / 사지 않는다**와 그 이유.
4. 냉정한 피드백 + 반박해야 할 주장 → 확인할 것 → 고친 결론 → 확정.
5. **'기다린다'면 다시 볼 조건을 적는다** (예: PER이 ○배 아래로 오면, 다음 사업보고서에서 이자보상비율이 1을 넘으면).
6. `분석기록.md`에 날짜와 함께 저장한다.
7. `analyses/회사이름/`에 세 가지를 md와 PDF로 만든다.
   - `회사이름_분석보고서`: 결론, 근거, 다시 볼 조건
   - `회사이름_검증표`: 결론에 쓴 수치마다 출처(공시·접수번호·절), 원문 대조 결과(일치/계산값/불일치), 계산값이면 계산식. 불일치면 고친 뒤 결론이 바뀌는지 다시 확인한다
   - `회사이름_역할구분`: `진행.md` 기록으로 만든 표. **기록에 있는 것만** 적는다

끝: 결론을 확정하고 세 문서를 만들면.

## 6단계: 보유 중 점검

`investor_profile.md`의 보유-①, 매도-①~③을 따른다.

- **보유 목록:** 사용자가 **샀다고 말하면** `analyses/_보유목록.md`에 추가한다 (회사, 산 날짜, 산 이유 = 그때의 최종 판단). 팔았다고 하면 기록을 남기고 목록에서 뺀다.
- **언제 점검하나**
  - 정기: 사업보고서가 나올 때 (1년에 1번). 뉴스와 시장 흐름도 함께 본다.
  - 바로: 대표이사 변경, 대규모 자금조달(유상증자·전환사채), 소송·제재·중대재해, 대주주 지분 변동

1. 지난 분석 기록과 **산 이유**를 보여준다.
2. 새 사업보고서나 바로 확인할 일에 해당하는 공시를 찾는다 → 요청 수를 알리고 승인 → 받는다.
3. **바뀐 단계만** 다시 계산하고, 산 이유가 여전한지 비교한다.
4. 판단: **계속 보유 / 일부 판다 / 판다** → 피드백 → 확인할 것 → 확정.
   - 파는 이유는 **회사가 바뀌었을 때**(숫자가 너무 나빠짐, 영업CF가 최근 5년 규모에서 벗어남, 경쟁사와 비교, 정성적 이유)와 **가격이 너무 올랐을 때**(내재가치를 크게 넘거나 경쟁사보다 높음).
   - **나눠서 판다.** 더 좋은 기회만으로는 팔지 않는다.
5. `분석기록.md`에 날짜와 함께 저장한다.

끝: 판단을 확정하고 저장하면.
